# P0-12B — Credential storage protocol (implementation slice 1)

Reviewed against PR #72 head `d7173c76b0c80928cf19a53e32c1ab2cd5317851`.

**Status: code foundation only. Not a completed SEC-03 remediation.** Existing OPDS repository, Room schema, and catalog UI are unchanged and still use the legacy columns. Do not treat this slice as encrypted production OPDS storage, or merge PR #72 into main on its strength.

## Source implementation

- `OpdsCredentialStorage.kt`: immutable generation references, credential-safe error and pair types, bounded strict UTF-8 envelope, verified write/read, origin/identity checks, and isolated retirement.
- `AndroidOpdsCredentialStorage.kt`: candidate DI adapter to the existing `PrivateGatewaySecrets` authenticated AES-GCM/no-backup backend. No weaker alias, no plaintext fallback, no key-policy change.
- `OpdsCredentialMigration.kt`: migration state machine and transactional journal interface. Legacy removal can occur only in the journal's atomic publish after storage verification. Cancellation or uncertain database acknowledgement never triggers immediate ciphertext deletion.
- `OpdsCredentialStorageTest.kt`, `OpdsCredentialMigrationTest.kt`: synthetic in-memory failure injection tests.

The versioned payload contains the canonical HTTPS origin and a matching username/password pair, serialized together. Base64 is only serialization, NOT encryption. The existing Keystore backend supplies authenticated encryption with storage ID as associated data. The generation namespace includes the durable catalog row ID and a fresh UUID, so changing titles, duplicate URLs, or replacing credentials cannot reuse an unrelated catalog generation. Origin changes require explicit replacement/removal by the future editor; a same-origin path edit does not invalidate credentials. Invalid input (including incomplete pairs, colon in Basic username, control characters, malformed UTF-8, oversized envelopes) is rejected; legacy rows with such values must remain recoverable rather than being silently cleared.

## Crash and concurrency contract for the next production integration

1. Add a nullable generation column to the catalog record and a durable journal recording catalog ID, generation UUID, and RESERVED/ACTIVE/RETIRED lifecycle. Retain the legacy columns solely for migration. Review non-destructive Room v3→v4 migration on Android and iOS, using their actual drivers. Test a real v3 upgrade fixture, including unrelated tables.
2. Insert new catalog metadata without plaintext credential columns; get a real stable row ID. Reserve the generation transactionally before any file write. New catalog creation needs explicit pending-state recovery so a failed authenticated save is not silently reported successful or left indistinguishable from an intentional anonymous catalog.
3. `reserve(expected, ref)` atomically compares ID, current catalog URL, current legacy pair and active generation to the snapshot and records a RESERVED entry. All writers must share the same catalog mutation mutex and compare-and-set discipline. Use a durable journal; the test fake is not an implementation of Room.
4. `writeVerified` commits the authenticated payload and reads back exactly the same versioned payload. An identical retry is allowed; a different payload for the same ref is rejected. Before production use, review power-loss durability of `PrivateGatewaySecrets.write` (atomic rename currently does not explicitly fsync file and directory). Read-back alone proves content correctness, not survival of abrupt power loss. Coordinate one singleton backend/key initialization across all users of its authenticated key; no concurrent key re-generation. Do not use this adapter for real credential migrations until these conditions are addressed and tested.
5. `publish(expected, ref)` must atomically compare the exact row plus reservation, write the new active generation, clear BOTH plaintext columns, and retire any previous generation. Never clear plaintext before this transaction. If commit acknowledgement is ambiguous, query durable state; never guess or delete the new file. Sanitize database exceptions at the repository boundary without swallowing coroutine cancellation.
6. `abandon(ref)` only retires an unpublished reservation, never an active generation. The reconciler must prove a generation unreferenced and not being written before calling `retire`. Use the same mutex for reconciliation; retain journal entries on clear failure and retry idempotently. A process crash may leave RESERVED entries or encrypted orphans; no broad key/alias/file deletion.
7. Traverse all legacy catalogs on an appropriate authenticated migration opportunity; do not rely on only catalogs visited by users. Keep a pending/recovery-required indication for incomplete/failed rows and never use plaintext on network failure. Ensure old SQLite page/WAL remnants are addressed with reviewed secure deletion/checkpoint handling, while acknowledging flash wear-leveling/previous copies limits. Null columns alone do not prove historical forensic erasure.
8. The active reference is durable even when decrypt is locked/missing/invalidated. `ALREADY_REFERENCED` only means no migration is needed; it is not proof the ciphertext can be read. Show a safe retry/recovery state rather than empty credentials. `readForRequest` requires the expected catalog ID and URL; foreign HTTPS origin returns null before decrypting. Invalid/non-HTTPS input fails. A missing referenced generation is an error, never a successful anonymous read.
9. Wire explicit Keep/Replace/Remove semantics, no prefilled secret, masked entry, safe snackbar errors and close-on-success. Require explicit replacement/removal for a changed origin if a credential exists. Handle duplicate URLs through stable selected catalog ID in ViewModel navigation and requests. Audit OkHttp redirects and cookie scoping; the PR #80 origin boundary must remain intact. Never leak actual credentials or private URLs in logs, saved state, diagnostics, backups or error messages.
10. Run blocking storage calls on the configured IO dispatcher. Keep the actual production migration, network and UI wiring behind the next reviewed slice; the new classes in this change are not called by existing app code.
